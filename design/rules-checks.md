# Design rules and their checks

Where the rules are, which scripts hold them, how to run them all, how to add one.

## Where the rules are defined

| File | What it is |
|---|---|
| `design/rules.md` | The catalogue for people: every rule by section, Kieran's quote, repeats and priority, the padding model. Hand-written. |
| `design/rules.json` | The same rules for tools: `id` (`SP-01`), `section`, `rule`, `quote`, `quote_ref`, `refs`, `repeats`, `priority` (P0, P1, P2), `components`, `proposed_check`, and the declared coverage `status` and `enforced_by`. Hand-written. A run never writes into it. |
| `design/rules-manual.json` | The rules no script can judge (a person looks), each with why. Hand-written. |
| `design/rules-report.md`, `design/rules-report.json` | The state of every rule after the last full run: passing, failing, not run, unenforced. Generated by `scripts/rules-check.py`; do not edit. |

An ID is `<section code>-<two digits>`. A check, a test name and a commit message cite it.

`status` and `enforced_by` in `rules.json` are what a person declared holds each rule. They say nothing about a run. The pass or fail of a rule is only in the report. The script validates the declaration against the checks (below).

## Which scripts enforce them

`make check` already runs the checks (`layout-check`, `overflow-check`, `state-check`, `copy-check`, `pixel-check`, `stability-check`, `motion-check`, `icons-check`, `ui-lint`, `taxonomy-check`). `scripts/rules-check.py` calls those same scripts and adds what they lack: the rule IDs of their findings gathered into one report per rule. Its table `CHECKS` holds only how to run each check. What each check enforces is **read from the check**: `python3 scripts/rules-check.py --registry` prints it.

| Check | Runs | Rule IDs come from |
|---|---|---|
| `ui-lint` | `scripts/ui-lint.py` (source, no app) | `RULE_IDS` and `RULE_MESSAGES` in the script |
| `taxonomy-check` | `scripts/taxonomy-check.py` (no app) | `RULE_IDS` in the script |
| `icons-map-fork`, `icons-build`, `icons-colour` | `scripts/icons/*.py --check` (no app) | `RULE_IDS` in each script |
| `icons-golden` | `scripts/icons/golden.py` (no app) | `[IC-01]` prefixes of its findings |
| `copy-lint` | `scripts/copy-lint.py` (`--offline`: source strings only) | the `(key, [IDs], message)` triples in the script |
| `layout-lint` | `scripts/layout-lint.py --parity --rtl` | `Meta { key, ids }` of `inspector/checks/mod.rs`, `[SP-01]` prefixes, and `RULE_IDS` for the older rules |
| `overflow-check` | `scripts/overflow-check.py` | `RULE_IDS` in the script |
| `state-check` | `scripts/state-check.py` | `Meta { key, ids }` of `inspector/state_checks/mod.rs` |
| `focus-ring-check`, `tooltip-check` | the scripts of those names | `RULE_IDS` in each script |
| `pixel-check`, `structure-stability`, `scroll-continuity` | the scripts of those names | the `Finding(key, [IDs], ...)` calls and scenario ID lists |
| `frame-gate` | `scripts/frame-gate.py` | `RULE_IDS` in the script |
| `loop-check`, `number-roll-check`, `nav-slide` | `loop-check.py --all`, the other two | `[BH-05]`-style prefixes and `RULE_IDS` |

The registry reads Python by its syntax tree (a `[SP-01]` in a message, a list of IDs after a rule key, `RULE_IDS`) and Rust by its `Meta` tables. Fixture code (`run_fixtures`) is skipped: its findings are made up. An ID in a docstring only is listed under "documented only" in the report and does not count as enforced. Every ID a check cites is looked up in `rules.json`; an unknown one is reported (and `python3 tests/rules-check.test.py` fails).

### Unit tests as a source

`tests/rules-tests.json` maps Rust test modules (`controls::tab_tests`, `shell::notice_tests`, ...) to the rules their tests hold, each with a one-line `covers` so a rule is never read as more covered than it is. The `unit-tests` check runs those modules (`cargo test --lib --features testing -- <module>:: ...` of `bingux-ui`, `--test-threads` = `--jobs`) and reads `test X ... ok|FAILED|ignored`: a rule held by tests passes when every test of its modules passed, fails with the failing test's path as the finding's location, and fails when a module of the map has no test left (the map is stale). The registry also checks the map without running: every ID exists, every module has a `#[test]` in the tree. `--offline` does not run it (it builds the test binary). The tests of the checkers themselves (`inspector/checks/tests.rs`) hold IN-05 only, not the rules their fixtures break. Add a row to the map when a test holds a rule; it is hand-written, with the doc comment and test names of the module as the evidence.

### Findings no rule holds, and findings by kind

A check can find a kind of defect that no rule of `rules.json` states. The check declares it in `RULE_UNMAPPED = {"key": "why"}` (`layout-lint.py`, `overflow-check.py`: `outside-parent`, a box reaching outside the box that holds it). Such findings are never dropped and never given a rule: they fail the check, and the report counts them in "Findings that hold no rule of the book" with the reason. A rule key the registry cannot place and that is not declared is listed under "layout-lint rule keys that cite no rule ID".

The report also counts every check's findings by kind (the rule key) and, for `overflow-check`, by scenario (baseline, pseudo, scale200, longdata, worst): "Findings by kind". The book has one rule for text under stress (TX-02), so its kinds (`wrapped`, `overflow`, `truncated`, `text-collision`, `overlap`, `clipped`, `hidden-label`, `horizontal-scroll`) all stand for TX-02; the table, not the rule's count, says what was found.

### Declared coverage against the registry

The report lists, from `rules.json`:

- a rule whose `enforced_by` names a check that does not cite the rule (the hand text is wrong, or the check does not hold it yet);
- a check that cites a rule whose `enforced_by` omits it;
- a rule declared `enforced` or `partial` that no check cites;
- a rule declared `none` or `design-only` that a check cites.

`python3 scripts/rules-check.py --sync-coverage` (off by default) appends the registry's checks to `enforced_by` as ` || registry: layout-lint[inset-asymmetry], ui-lint`, replacing an earlier registry segment, and writes only that field: never `status`, never the outcome of a run. It refuses a `rules.json` that is not in the `json.dumps(indent=1)` format, so the diff is those lines only.

## How to run

```sh
make rules-check                        # every check, then design/rules-report.md and .json
make rules-check ARGS=--offline         # the quick checks that start no app; report goes to /var/tmp/rules-check/latest
make rules-check ARGS="--only ui-lint,copy-lint"
make rules-check ARGS="--skip layout-lint,state-check"
make rules-check ARGS="--reuse /var/tmp/rules-check/latest"   # a check's output from an earlier run, when it has one
make rules-check ARGS=--strict          # also fail on known open defects, unenforced P0 rules and declared-coverage drift
python3 scripts/rules-check.py --registry       # the registry and its integrity problems, no run
python3 tests/rules-check.test.py
```

Each check runs one at a time through `scripts/app_env.py` (memory GSettings backend, no `WAYLAND_DISPLAY`, no `DISPLAY`). `--jobs N` (default `JOBS`, 2) is how many captures one check renders at once. Raw output, one log and one metadata file per check, is kept in `--out` (default `/var/tmp/rules-check/latest/raw`); a check's captures go to a scratch directory that is removed when it finishes. The apps are the binaries already built under `CARGO_TARGET_DIR`; `--build` lets the checks build them first, and the report says when a binary is older than the source.

A full run writes `design/rules-report.*`. An `--offline`, `--only` or `--skip` run writes the report into `--out` instead, so a partial run never replaces the full one (`--write-report` overrides, `--no-report` writes none). `--reuse DIR` takes a check's output (and the time it ran) from the `raw/` folder of an earlier run, unless that run measured a different scope; the report marks it `reused`. `--arg state-check="--timeout 1800"` appends options to one check's command (a slow machine, a narrower run).

Exit status is 1 when a rule is failing or a check is red or errored; `--strict` adds the cases above. `make rules-check` is not part of `make check`: `check` runs the checks themselves and fails on their findings, `rules-check` is the report on top.

**Stale binaries.** Each check that renders an app records, when it finishes, which of the three debug binaries (`bingux-settings`, `bingux-taxonomy`, `bingux-files`) is older than a source file in its own cargo dep-info (`target/debug/<name>.d`, plus the `Cargo.toml` of its package and of bingux-ui). A check that measured an older binary is `partly run`, never `passing`, with a note naming the binaries, and the exit status is 1. The report's header lists each binary's build time and the newest source it was built from. `--allow-stale` turns the guard off (the header says so). Output taken with `--reuse` from a run that did not record freshness counts as stale.

## What a status means

The status is in the report only.

| Status | Evidence |
|---|---|
| enforced+passing | every check that cites the rule ran in this run, to the end, and found nothing |
| enforced+failing | a check found it violated: the findings and their locations are in the report |
| enforced+known-open | only findings the check lists as known open defects (`KNOWN` of `state-check.py`, or a line the check prints as `note:`); they do not fail the check |
| allowlisted | findings exist and every one is covered by an `ALLOWED` entry with a reason |
| not run | a check cites it but was not executed (`--offline`, `--only`, `--skip`) |
| partly run | some of the checks that cite it ran clean and others did not run, or a check that cites it did not finish its job (a capture timed out or crashed, a sweep stopped early): its zero findings are not a pass |
| errored | a check that cites it exited non-zero, named no finding and did not finish (a crash, a missing binary, a time-out); no verdict. A check red only because an allowlist entry matched nothing is `red`: what it measured stands |
| unenforced | no check cites it |
| manual | no check can judge it (`design/rules-manual.json`) |

A rule is never reported passing from a check that did not run. A check run with `--reuse` shows `[reused output]` beside its statuses. A check that ran with a narrower scope (`copy-lint --no-captures`) shows its scope. A finding with no rule ID (a layout rule that holds no rule of the book yet, such as `clipped`) is counted as "no rule ID" for its check and still turns the check red.

## Add a rule

1. Add it to `design/rules.json` (`id`, `section`, `rule`, `quote`, `quote_ref`, `quote_date`, `refs`, `repeats`, `priority`, `components`, `proposed_check`, `status`, `enforced_by`) and bump the section's `count`. Add it to `design/rules.md`.
2. Pick the check that holds it, or write one (below). Cite the ID in the check: in the finding's message (`[SP-21] ...`), in a `(key, [IDs])` pair, in the `ids` of a Rust `Meta`, or in the script's `RULE_IDS`.
3. If no script can judge it, add it to `design/rules-manual.json` with the reason.
4. `python3 scripts/rules-check.py --registry` shows what the check cites and what is out of line; `--sync-coverage` brings `enforced_by` up to date. `python3 tests/rules-check.test.py` fails when a check cites an ID the book does not have, or cites none.

## Add a check

1. Write the script. It exits non-zero on a finding, prints each finding on a line of its own (or writes `--json FILE`, a list of `{rule, capture, target, what, allowed}` or the probe form of `scripts/probe_lib.py`), and carries rule IDs as above. A text-only script that prints findings with no ID declares `RULE_IDS = {"key": ["XX-01"], "*": [...]}` (`*` is the default for a finding no key matches) and `RULE_MESSAGES = {"key": r"regex that picks that kind of line"}`.
2. Add one `Check(...)` line to `CHECKS` in `scripts/rules-check.py`: its id, script, arguments, parser, whether it takes `--json`, `--jobs` and `--build`, `offline_args` if it needs no app, and `aliases` if `rules.json` names it differently from its id.
3. Add the Makefile target and a line in `CONTRIBUTING.md` as the other checks have.
4. `python3 scripts/rules-check.py --registry`, then `--sync-coverage` if you want `enforced_by` to follow.

## Allowlist a finding, with a reason

Each check keeps its own list; every entry has a rule key, where it applies and a reason, and an entry that matches nothing fails the check so a list cannot rot. Nothing is allowlisted in `rules-check.py`.

- `scripts/layout-lint.py`, `scripts/state-check.py`, `scripts/pixel-check.py` and the others: `ALLOWED` (`rule`, `capture` regex, `where` regex, `why`). `state-check.py` also has `KNOWN` for a defect that is open and not fixed, each with what is wrong.
- Rust rules: `ALLOW` in `inspector/state_checks/mod.rs`, `EXEMPT` and `NOT_BUTTONS` in `inspector/checks/mod.rs`, each with `reason`.
- `scripts/ui-lint.py`: `BLOCKING_ALLOWED`, `RAW_PRESS_ALLOWED`, `LAUNCH_ALLOWED` (file -> reason), or `ui-lint: allow(...)` on the line.
- `scripts/copy-lint.py`, `scripts/taxonomy-check.py`: their `ALLOWED` list and `packages/bingux-taxonomy/coverage-allowlist.txt`.

The report lists every entry with its reason and how many findings of the run it covered (`matched`; blank for entries applied inside the app).
