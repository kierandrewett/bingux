### What a folder does now (the decision)

**A folder with fewer than two apps is dissolved.** Removing an app from a
two-app folder removes the folder: the remaining app takes the folder's slot and
the app taken out follows it. Reasoning, from this dock rather than from other
platforms: a dock slot is the scarcest thing a dock has, a folder of one app
only adds a click, and the folder card is the only place the user would ever
see it. Platforms differ here (I did not verify how iOS, Android launchers,
GNOME or macOS each treat a one-app folder in this session, so the docs claim
none of them). Dissolving is also the only rule that keeps the saved file free
of states the UI cannot make.

## Tests this branch adds

- `tests/dock-folders.test.mjs`: the model in `DockFolders.js` (29 cases:
  create, add, remove, reorder, rename, recolour, ungroup, the one-app
  collapse, cleaning an older file, preview grid, paging, keyboard steps, schema
  limits). No display needed.
- `tests/dock-folders.py` and `tests/dock-folders.qml`: the production Dock
  and card in a private headless Sway. `model` and `legacy` (no saved
  `dock_apps`) check every operation and read the saved file back through
  `bingux-config`; `pointer` drives a virtual pointer and keyboard (drag to make
  a folder, type a name, arrows, Ctrl+arrow, Enter, drag out, drop into a
  folder, reorder in the card, drop on the dock row, plain reorder, saved order)
  at dock sizes 56, 36 and 80, aligned centre, left and right, in normal and
  reduced motion.
- Checked to fail without the fix: with the model's minimum set to one, four
  model cases and the `model` scenario fail; with the old hit-testing and
  immediate reorder preview, the pointer scenario fails at its first step (the
  two apps are reordered and no folder exists).
